# Plano de Implementação

## Contexto
App Next.js 16 + Prisma + Neon PostgreSQL + Clerk + shadcn/ui + Zod + react-hook-form.
O build já passa. O usuário quer resolver 5 pontos específicos antes de seguir com novas features.

## Pontos a Resolver

### 1. Gráfico de receita mensal usa dados mockados
**Arquivos:** `src/app/actions.ts`, `src/app/(dashboard)/page.tsx`
**Problema:** O array `receitaMensal` está hardcoded no dashboard.
**Solução:**
- Criar Server Action `getReceitaMensal(months = 6)` que busca pagamentos do tipo `'juros'` dos últimos N meses.
- Agrupar por ano-mês (ex: `2026-01`) e somar os valores.
- Retornar array no formato `{ mes: string, valor: number }` com nomes dos meses abreviados em português.
- Substituir o mock no `page.tsx` pela chamada real.

### 2. Recibo PDF calcula saldo restante errado
**Arquivos:** `src/app/actions.ts`, `src/app/(dashboard)/pagamentos/page.tsx`
**Problema:** Linha 75 de `pagamentos/page.tsx` passa array vazio para `calcularSaldoDevedor`.
**Solução:**
- Alterar `getPagamentos` para incluir `pagamentos` dentro do `emprestimo` no relacionamento (`include: { emprestimo: { include: { cliente: true, pagamentos: true } } }`).
- No `page.tsx`, passar `emprestimo.pagamentos` para `calcularSaldoDevedor`.
- Atualizar o tipo `Pagamento` em `src/types/index.ts` para refletir `emprestimo.pagamentos?: Pagamento[]` (ou criar um tipo estendido local se preferir).

### 4. Não há validação nos forms (Zod não usado)
**Arquivos:** `src/components/cliente-form.tsx`, `src/components/emprestimo-form.tsx`, `src/components/pagamento-form.tsx`, novo `src/lib/schemas.ts`
**Problema:** Zod e `@hookform/resolvers` estão instalados mas não usados. Campos obrigatórios não têm validação estruturada.
**Solução:**
- Criar `src/lib/schemas.ts` com 3 schemas Zod:
  - `clienteSchema`: nome (string, min 2), cpf_cnpj (string, optional), telefone (string, optional), email (string, email, optional), endereco (optional), observacoes (optional), ativo (boolean, default true).
  - `emprestimoSchema`: cliente_id (string, uuid), valor (number, > 0), taxa_juros (number, >= 0), data_inicio (string, date), data_vencimento (string, date, optional), observacoes (optional), status (enum, default 'ativo').
  - `pagamentoSchema`: emprestimo_id (string, uuid), valor (number, > 0), data_pagamento (string, date), tipo (enum 'parcial'|'juros'|'quitacao'), observacoes (optional).
- Refatorar cada form para usar `react-hook-form` + `zodResolver`.
- Exibir mensagens de erro abaixo de cada campo inválido usando componentes de UI existentes (ex: `<p className="text-sm text-red-600">`).
- Desabilitar botão de submit enquanto `!formState.isValid` (ou manter habilitado e deixar o Zod bloquear).

### 5. Rotas [id] de empréstimos/clientes
**Arquivos:** `src/app/(dashboard)/clientes/[id]/page.tsx`, `src/app/(dashboard)/emprestimos/[id]/page.tsx`, `src/components/clientes/clientes-table.tsx`, `src/components/emprestimos/emprestimos-table.tsx`
**Problema:** As rotas existem mas a página de cliente está "pobre" (só mostra dados cadastrais e lista simples de empréstimos sem saldo).
**Solução:**
- Em `clientes/[id]/page.tsx`:
  - Calcular e exibir: total emprestado ao cliente, saldo devedor total (somando todos os empréstimos ativos), total de pagamentos recebidos.
  - Usar `calcularSaldoDevedor`, `calcularJurosAcumulados`, `calcularJurosPendentes` com os pagamentos reais de cada empréstimo.
  - Tornar a lista de empréstimos navegável (já tem link implícito? Não, adicionar link para `/emprestimos/${e.id}`).
- Garantir que as tabelas já tenham os links para detalhes (já têm botão Eye com Link — confirmar que está funcional).

### 6. Sem tratamento de erro nas Server Actions
**Arquivos:** `src/app/actions.ts`, todas as pages que chamam actions (`clientes/page.tsx`, `emprestimos/page.tsx`, `pagamentos/page.tsx`, `relatorios/page.tsx`, `login/page.tsx` se houver server action lá).
**Problema:** Se o banco falhar, o app crasha silenciosamente ou com erro não tratado na UI.
**Solução:**
- Refatorar TODAS as Server Actions em `actions.ts` para retornar um padrão unificado: `Promise<{ success: true; data: T } | { success: false; error: string }>`.
- Envolver lógica Prisma em `try/catch`; em caso de erro, retornar `{ success: false, error: error.message || 'Erro inesperado' }`.
- Nas páginas, verificar o retorno antes de atualizar estado local. Se `!success`, exibir `alert(error)` (solução mínima sem adicionar nova lib de toast; se o usuário preferir outra coisa, pode evoluir depois).
- Garantir que o estado de loading não fique preso em caso de erro.

## Riscos & Decisões
- **Padrão de retorno das actions:** Mudar o contrato de todas as actions exige atualizar todos os callers. Isso é mecânico mas extenso. Aceitável pois o app é pequeno (~5 pages).
- **Toast/alert:** Sem lib de toast instalada, usaremos `alert()` para erros. É feio mas funcional. O usuário pode trocar por Sonner/shadcn toast depois.
- **Prisma include aninhado:** Incluir `pagamentos` dentro de `emprestimo` no `getPagamentos` aumenta o payload, mas é necessário para o cálculo correto do saldo no recibo. O volume de dados é pequeno para um app de gestão local.

## Ordem de Execução Sugerida
1. **Ponto 6** primeiro (tratamento de erro nas actions) porque muda o contrato de todas as actions e seus callers.
2. **Ponto 4** (validação Zod) porque é isolado nos forms.
3. **Ponto 2** (recibo PDF saldo) porque depende da action `getPagamentos`.
4. **Ponto 1** (gráfico real) porque depende da nova action.
5. **Ponto 5** (rotas [id] melhoradas) por último, pois é polimento de UI.

## Validação
- `npm run build` deve passar sem erros de TypeScript.
- Navegar pelas 5 telas principais (Dashboard, Clientes, Empréstimos, Pagamentos, Relatórios) sem crash.
- Testar criação de cliente/emprestimo/pagamento com dados inválidos para confirmar validação.
- Testar exclusão de empréstimo/cliente para confirmar que erros mostram alert.
- Verificar gráfico do dashboard com dados reais (se houver pagamentos do tipo juros no banco).
- Verificar recibo PDF com saldo calculado corretamente.
